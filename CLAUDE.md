# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Honu is a native desktop GUI app written in Rust (edition 2024) using **eframe/egui 0.37** — an experiment in desktop GUI design that departs from Windows/macOS conventions. It currently renders draggable, window-like bubbles (some opaque, some translucent glass) that float directly on the real macOS desktop, above all other windows. Only the turtle's place persists across launches, through eframe's `persistence` feature (`~/Library/Application Support/Honu/app.ron` on macOS; delete it to reset); everything else is in-memory.

## Commands

```sh
cargo run                    # build and launch; bubbles float on the real desktop (quit with ⌘Q)
cargo run -- --windowed      # launch in an ordinary window with its own wallpaper instead
cargo build --release        # optimized build
cargo clippy --all-targets   # lint
cargo fmt                    # format (cargo fmt --check to verify)
cargo test                   # run tests (physics simulations in src/view/physics.rs)
cargo test <name>            # run a single test by name filter
trunk serve                  # build the web version and serve it at http://127.0.0.1:8080 with live reload
trunk build --release        # optimized web build into dist/
cargo clippy --target wasm32-unknown-unknown   # lint the web build too
```

CI (`.github/workflows/ci.yml`) runs the format check, both clippy builds (warnings are errors), and the tests on Linux for every push, and clippy and the tests on macOS for pull requests only. In Claude Code cloud sessions, `.claude/hooks/session-start.sh` installs clippy, rustfmt, and the wasm target and fetches the crates.

The web version needs `rustup target add wasm32-unknown-unknown` and [trunk](https://trunkrs.dev). It is the `--windowed` experience in a browser: it cannot float on the desktop, and the turtle's menu has no Exit there, since quitting means nothing in a page. Web-only files live in `web/` (the page is `web/index.html`, whose asset paths are relative to `web/`); `Trunk.toml` at the root points trunk there and writes the build to `dist/`.

## Architecture

The code follows MVC. Each **microapp** (Notes, Ask AI) is a controller that keeps its own model: any number of items, such as notes. A **bubble** is only a view of one item, pointing at it by id. The **shell** wires microapps, the stage of bubbles, and the two sprites (the turtle and the octopus) together.

- `src/main.rs`: only the two `main()`s, picked by `target_arch`. The web one (`wasm32`) starts `HonuApp` in the `<canvas id="honu">` of `web/index.html` through `eframe::WebRunner`, never floating; keep platform-specific code behind `cfg` so both targets build. The native `main()` configures the window (`NativeOptions` / `ViewportBuilder`): by default transparent, borderless, and always on top, maximized after the first frame to cover the screen except the menu bar and Dock; with `--windowed`, an ordinary window that paints its own wallpaper. The window and Dock icon is `assets/icon.png`, embedded at compile time and rendered at 512×512 from its source `assets/icon.svg` (the README illustration lives separately in `docs/images/`).
- `src/shell.rs`: `HonuApp`, the whole app inside the window: a `Registry` of microapps, a `Stage` of bubbles, the turtle, the octopus, and the turtle's menu. The app starts with only the turtle on screen; every bubble comes from its menu. `impl eframe::App for HonuApp` allocates one full-window painter, and `ui` runs one frame in steps: `lay_out`, `update_octopus`, `handle_input`, `update_bubbles`, `update_cursor`, and `paint`. What the user is in the middle of is one `Interaction` (idle, dragging the turtle or a bubble, the menu open, or the menu just dismissed by a press on the turtle), and what is under a point is one `Hit`, from the top layer down: the open menu, the turtle, the octopus, then the bubbles; input, click-through, and the cursor all go by `hit`. Each frame `update_bubbles` runs the microapps' `update`, sets every bubble's label and breathing from its microapp, applies the `Effect`s they asked for, and steps the stage. `paint` then paints each bubble followed by its content (if open, drawn by its microapp through `content_ui`), so content stacks correctly, and paints the octopus and then the turtle last, above everything. Only the top bubble's content takes input, so bubbles lying over another's content can still be grabbed. `save` and the end of each turtle drag store the turtle's offset from the window center, under separate keys for floating and `--windowed`; the drag-end save matters because quitting with ⌘Q or from the Dock exits without calling `save`. Window and egui-memory persistence are turned off. Clicking the turtle with either button (or tapping it) opens `TurtleMenu` where the pointer is, a foreground `egui::Area` with one item per microapp (`menu_label`: Add Note, Ask AI) and (desktop only) Exit; a microapp's item starts a new item there (`HonuApp::start`), and the turtle spits out a bubble showing it. Text typed while no field has the focus goes to the newest bubble the turtle spat out (`TypeAhead`), and is handed to its microapp in the `View` (`typed_ahead`) the first time that bubble takes input, so no keystroke is lost before its field can take the focus. While the menu is open the floating window takes every click, and a press outside it or Escape closes it (a press on the turtle leaves `Interaction::MenuDismissed`, so its click does not reopen the menu). The shell keeps the `Services` the microapps share and stores what changed in them after drawing the content.
- `src/services.rs`: `Services`, what the microapps share through their `Context`: the `ApiKey`, which notes its changes so the shell can store them, and the `claude::Client` to ask Claude with (a `claude::Fake` in tests). The key comes from `ANTHROPIC_API_KEY` (loaded from `.env` by `dotenvy`) on the desktop, where a pasted key is kept only in memory; on the web a pasted key is kept in local storage, and a key the API refuses is cleared.
- `src/microapp.rs`: the `MicroApp` trait and what goes with it. A `Bubble` points at one item with a `ViewTarget` (`AppId` + `ItemId`), so a microapp can have any number of bubbles. A microapp gives its items' `appearance`, `title` (the bubble label), and `is_busy` (breathing), draws an item in an open bubble (`ui`, which may return the panel height that fits), and catches up on background work in `update`. Each bubble also owns a `ViewState` the microapp makes for it (`new_view`), for what belongs to that one view rather than to the item, such as a draft or whether its text field still has to take the focus; the microapp gets it back, with the bubble's `BubbleId` for salting widget ids, in the `View` it draws into. `focus_at_end` focuses a text field with the cursor after its text. It works through a `Context`, which carries the shared `Services` and collects the `Effect`s it asks of its bubbles, such as a `Gesture` for every bubble showing an item. An item is deleted (`remove`) once the octopus forgets the last bubble showing it. `Registry` holds the microapps in menu order and routes each `ViewTarget` to its microapp. To add a microapp, implement the trait in `src/apps/` and list it in `HonuApp::new`.
- `src/apps/notes.rs`: the Notes microapp, any number of notes (`Note`), each a multiline text field; a new bubble's `NoteView` makes it take the focus when it first opens. A note's bubble is labeled with its first line with text (`view::bubble::short_label` keeps labels short).
- `src/apps/ask.rs`: the Ask AI microapp, any number of `Chat`s (the model), each shown through a `ChatView` (the key draft, a refused key's error, and focus). When a chat needs the user to type again, it counts up `focus_requests`, and each view takes the focus once per request. A chat asks for an API key if there is none, then for a question, then shows the answer as it streams in, returning the height that fits so the panel (`Bubble::set_panel_height`) grows with the answer. `update` polls every chat's stream and turns how a question ended (`Outcome`) into a `Rise` or `Wobble` gesture effect, and `is_busy` makes a chat's bubbles breathe while Claude works.
- `src/stage.rs`: `Stage`, every bubble in back-to-front paint order (pressing on a bubble moves it to the top), each with a `BubbleId` it hands out in `add`, and how they are hit-tested, dragged (the dragged bubble is always the top one, and new bubbles go below it), opened, spat out (`spit_panel`: a new bubble flies out of the turtle's mouth and opens on landing, stepping aside from any panel already there, as windows cascade), and stepped (`step` animates them and runs the physics). Bubbles swallowed by the octopus stay on the stage, out of reach and out of sight (the shell skips painting them), until the octopus forgets them and they are `remove`d; `front` is the front bubble not swallowed, whose content alone takes input. It knows nothing of what a bubble shows.
- `src/view/bubble.rs`: `Bubble` and its outline `Shape`, a rounded rectangle with superellipse corners and a lit rim. A closed bubble is a rounded square like a macOS app icon; double-clicking toggles `open`, and the bubble then morphs (with a small overshoot) into a larger panel that shows its item. Bubbles show what they are doing through motion: `set_busy` makes one breathe (only the drawn outline, `display_shape`, swells, so content and hit-testing hold still), and `play` runs a short `Gesture` that moves the whole bubble and returns it: `Rise` when a task finishes, `Wobble` when the user is needed. A new bubble comes out of the turtle's mouth small and grows (`scale()`) as it flies to its place along its own path (`spawn_from`). `shrink` scales the whole outline, for a bubble held over the octopus or swallowed by it; content shows only at full size.
- `src/view/physics.rs`: per-frame motion, stepped by the stage before painting. Released bubbles keep the pointer's velocity and slow down with friction, idle bubbles drift with a slow per-bubble float, crowded bubbles push each other apart with a damped soft collision that passes momentum on (partial overlaps are allowed so the glass stays visible), and bubbles bounce off the window edges. Open bubbles can be thrown but neither float nor push, and spawning bubbles are left out of the simulation until they land. The app repaints continuously.
- `src/view/render.rs`: all custom drawing. Bubbles are vertex-colored meshes of nested rounded-rectangle outlines with superellipse (continuous-curvature) corners shaded on the CPU by a small lighting model (diffuse/specular, Fresnel rim for glass); there are no custom shaders, so true background blur/refraction is not implemented (planned in `TODO.md`).
- `src/sprite.rs`: `Grid`, shared by the two pixel-art sprites: converts sprite pixels (`PIXEL` points square) to points, finds the pixel under a point (so hit-testing can skip transparent pixels), and paints a sprite as one mesh of square, unblended pixels.
- `src/sprite/turtle.rs`: the pixel-art sea turtle, which starts in the bottom-left corner and can be dragged anywhere inside the window, drawn from a character grid, one character per pixel. It bobs while idle, hops when clicked, and briefly opens its mouth (`spit`) for each bubble; hit-testing ignores its transparent pixels.
- `src/sprite/octopus.rs`: the pixel-art octopus that deletes bubbles, drawn like the turtle. It rises from the bottom edge, in the corner away from the turtle, only once a bubble has been dragged `SUMMON_DISTANCE` away from where it was picked up, and sinks again afterwards, so it never sits on the desktop. Whether the *pointer* is within `REACH` decides a drop, not where the bubble lands, so a throw never deletes anything; a bubble held there shrinks (`Bubble::set_doomed`) and one dropped there is swallowed (`swallow_into`). The octopus only remembers which bubbles it swallowed (by `BubbleId`) and where they were picked up; the bubbles stay on the stage. They can be brought back for `UNDO_SECONDS`, while it shows "Click to undo"; clicking it or the hint (which `contains` counts as part of it) or ⌘Z (unless a text field has focus) spits the latest one back to where it was picked up (`Stage::spit_back`). After that `update` returns their ids, the shell takes them off the stage, and removes any item no other bubble shows from its microapp, which also cancels a chat's stream. Like the turtle it is painted above all bubbles and hit-tested before them.
- `src/desktop.rs`: reads the global mouse position (CoreGraphics on macOS). While floating, the window lets mouse events through (`ViewportCommand::MousePassthrough`) except when the mouse is on a bubble, the turtle, or the octopus; since a pass-through window gets no pointer events, this global position is polled every frame to decide.
- `src/claude.rs`: the `Client` trait microapps ask Claude through, and `Api`, which asks through the Messages API over raw HTTP (`ehttp`, which streams both natively and in the browser; there is no official Rust SDK), parsing the server-sent events into `Event`s on a channel. Uses `claude-opus-5-5` at low effort with `fallbacks: "default"`; the web build adds the `anthropic-dangerous-direct-browser-access` header that browsers need. A 401 comes back as `KeyRejected`. `Fake` stands in for the API in tests: it records the questions and lets the test send each answer's events.

egui is **immediate mode**: `ui()` runs every frame and rebuilds the whole interface from the current state, so UI changes are made by mutating `HonuApp` fields, not by holding widget handles.

Note that egui 0.37's `App` trait uses `fn ui(&mut self, ui: &mut egui::Ui, frame: &mut eframe::Frame)`; older egui examples online use `fn update(&mut self, ctx: &egui::Context, ...)` and won't compile as-is.

## Conventions

- Everything in the repository must be in English: identifiers, comments, UI strings, docs, and commit messages — even when the conversation is in Chinese.
- After changing Rust code, run `cargo clippy --all-targets` and `cargo fmt --check` before reporting the work as done, and fix any warnings they raise.
- The Claude API key lives in `.env` at the repository root as `ANTHROPIC_API_KEY` (the name the Anthropic SDKs read). `.env` and `.env.*` are git-ignored; only the empty template `.env.example` is committed. Never read, print, or commit `.env`, and never put a key anywhere else in the repository.
